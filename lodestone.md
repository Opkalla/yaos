# Lodestone Documentation

## Definitions

**Host** — the Cloudflare Worker (server) that all vaults in a sync network connect to. Every vault requires a host to function. The host stores the CRDT state, relays WebSocket connections between devices, and optionally stores attachments in R2. All vaults in the same sync network share the same host URL and sync token.

**Hub** — a vault that shares its notes outward to one or more spoke vaults. The hub's content is pushed to connected spokes in real time. A vault becomes a hub by clicking "Start sharing" in settings or by having a spoke register with it via an invite link.

**Spoke** — a vault that receives shared notes from a hub vault. A spoke connects to a hub using the hub's vault ID. Because hub and spoke must be on the same host, the spoke uses its existing host connection — no separate host URL or token is needed during spoke registration.

**Vault ID** — a randomly generated 16-byte base64url string that uniquely identifies a vault's CRDT room on the host. All devices syncing the same vault must use the same vault ID.

**Sync token** — the shared secret (password) for the Cloudflare Worker. Worker-global: every vault connecting to the same host uses the same token. Set as `SYNC_TOKEN` on the server, or generated during the browser claim flow.

## Sync modes (`syncMode`)

| Value | Meaning |
|-------|---------|
| `standalone` | Default. Connected to a host but neither sharing notes nor following a hub. |
| `hub` | Sharing notes outward. Connected spokes receive this vault's content. |
| `spoke` | Following a hub. Receives shared content from the hub vault. |
| `hub+spoke` | Both simultaneously — sharing notes to spokes while also following a hub. |

## Invite URL format

```
obsidian://lodestone?action=spoke&host=HOST_URL&hubVaultId=VAULT_ID&token=TOKEN
```

- `host` and `token` are only applied if the receiving vault has no server connection yet (bootstrap case). If already connected to the same host, the existing connection is reused.
- A spoke must be on the same host as its hub. Cross-host hub/spoke relationships are not supported.

## Rooms (collaboration model)

**Room** — An isolated collaboration space with its own Yjs Y.Doc and its own Cloudflare Durable Object. Each room has a unique PIN (`roomId`), generated by the hub and completely separate from any vault's personal identity. All members of a room connect to the same DO room, giving real-time WebSocket sync and live cursors. A room contains only what the hub chose to share.

**Hub** — A vault that creates a room and selects which folders to share into it. The hub edits those folders normally; changes propagate to all spoke vaults in real time. Everything in the hub vault that is NOT explicitly added to a room stays completely private and never reaches the server.

**Spoke** — A vault that joins a hub's room via an invite link. The hub's shared folders appear in a designated folder on the spoke. The spoke can read and edit those files collaboratively in real time alongside the hub and other spokes. The spoke's own files outside the room folder are private and unaffected.

**Private files** — Any file or folder in the hub vault that has not been added to a room. These never enter any Y.Doc, never reach the server, and are never visible to any spoke. Private is the default — content must be explicitly opted in to a room.

**Multiple rooms** — A hub can create multiple rooms simultaneously, each with a different folder set and a different group of spokes. A vault can also be a spoke in multiple rooms at the same time. Each room is a separate connection, a separate Y.Doc, and a separate folder on the spoke side. Rooms do not interact with each other.

**Per-room server topology** *(v3.3.0+)* — A room does not have to live on the same Cloudflare Worker as its hub's main vault connection. `RoomConfig` carries optional `host`/`token` fields; when unset, the room falls back to the vault's own main connection (the only behavior that existed before this). Each hub runs its own Worker for the rooms it hosts — a vault that is a spoke in someone else's room and a hub of its own room at the same time can have both on completely separate infrastructure. Within one Worker, every room still gets its own Durable Object instance (keyed to the `roomId`), which holds that room's Y.Doc and handles WebSocket connections.

**Room-scoped invite tokens** *(v3.3.0+)* — Invite links do not carry the vault's master sync token. The hub mints a token scoped to that one room's own Durable Object (`POST /vault/{roomId}/room-token`, master-token-authenticated) and embeds that instead. A room-scoped token authorizes WebSocket sync and blob access for that one room only — never the vault's main sync, snapshots, debug routes, or any other room. This is a server-side check (`verify-room-token` on the room's own DO), unlike the structure gate below.

**Room-only mode** *(v3.4.0+)* — A vault does not need a host of its own to participate in rooms. A spoke that joins an invite gets that room's `host`/`token` from the invite link, so the room syncs even when `settings.host`/`settings.token` are empty. This is a supported configuration, not a broken one: the plugin starts these "independent" rooms (those carrying their own host+token) during `onload`, before the personal-connection gates, and registers vault events so local edits still flow into the room. Rooms that *inherit* the vault's connection start later, after personal sync has reconciled. Consequences worth knowing: the status bar reports rooms separately from the personal sync (`Lodestone: 1/1 rooms connected` when there is no personal host, `CRDT: Connected · 1/1 rooms` when there is), each room card in settings shows its own live connection state, and **creating** a room still requires the vault's own host — the room is hosted on it — while **joining** never does.

**Room access tiers** *(v3.5.0+)* — The hub sets, per room, what spokes may do: `read-only` (spokes receive live updates but write nothing back — their editors are made non-editable so yCollab cannot push keystrokes), `hub-notes` (the default: spokes edit the hub's existing notes, but create/rename/delete stay hub-only), or `full` (spokes may also create, rename, and delete). The hub is never gated by its own room's tier. The value is published by the hub into the room Y.Doc at `sys.roomAccessTier` — the Y.Doc is authoritative, so a hub-side change reaches connected spokes live and a spoke that was offline converges on next sync; a spoke also stores the tier from its invite link (`&tier=`) for the window before the first sync completes. An unrecognized value normalizes to the default rather than to full access. Gated write paths: content edits, new-file seeding, rename, and delete. A blocked write shows the spoke a notice (deduplicated per path) explaining why, rather than silently dropping it. Same client-side-only caveat as below.

**Before v3.5.0, "structure is host-only" was incidental, not enforced** — the only thing that stopped a spoke's new note from propagating was `getRoomSyncAndCrdtPath` failing to match it against the room; a note created *inside* the aliased shared folder did match, and did sync to the hub. The tier gates above are what make the documented behavior actually true. Do not cite pre-3.5.0 behavior as evidence that a write path is closed.

**Structural write-gate is client-side only** — "only the hub can create/rename/move/delete files in a room" (see Constraints) is enforced by the plugin — the client simply never routes a spoke's structural change into the shared Y.Doc. It is not enforced by the server, and a modified or malicious spoke client could bypass it. This is a deliberate, documented tradeoff (see PROJECT-PLAN.md 4.10), not an oversight — do not describe it elsewhere as a security boundary.

## Constraints

- A vault can only act as a Hub for **one vault instance**. A single vault cannot simultaneously host multiple independent sync groups.
- Within a room, structural changes (create/rename/move/delete) are host-only unless the hub sets that room to `full` — enforced client-side, see above.
- Vault size target: ~50 MB (see `engineering/warts-and-limits.md` for canonical limits).
